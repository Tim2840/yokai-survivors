# 收尾一批改動

這個專案的使用者是獨立開發者，在手機上看回報、不看程式。收尾做得完整，他才能放心往下一步；漏一步（沒更新紀錄、沒截圖、說修好了其實沒驗證）會讓他失去信任。照下面順序做。

## 1. 自己先檢查（測試時不要改 src）

```bash
npm run typecheck && npm test
```

回歸測試要開著 vite（`curl -s localhost:5173` 不通就 `nohup npx vite --port 5173 &`，剛開要先載一次 `curl -s localhost:5173/src/main.ts`）。依改到的地方挑 id：

| 改到 | 跑 |
|---|---|
| 升級選卡、卡片、稀有度 | r2、v1、l1 |
| 技法、進化、技法格子 | v1、v2、g1 |
| 關卡流程、敵人生成、頭目、事件 | r1、e3、p1 |
| 地圖要素 | e1、e2 |
| 大招 | u1 |
| 手感、特效、擊殺爆圈 | f1、p1 |
| 河童或任何「所有角色共用」的東西 | y1（會掃有沒有別的角色的字） |
| 鏡頭、操作 | c1（很慢，約 8 分鐘）、i1 |
| 任何畫面或效能有關 | p1（draw call 手機 ≤ 80、程式數不變） |

```bash
NODE_PATH=node_modules node scripts/regress.mjs --only <id,id>   # --list 看全部
```

測試失敗時先找原因再改，不要放寬門檻；真的要改預算，在測試裡寫清楚理由（例：p1 的三角形預算有寫為什麼加）。**原因沒查清楚、沒在使用者實際看到的那份檔案上重現，就不要說修好了。**

## 2. 影響玩家的改動 → 更新紀錄

- `src/game/changelog.ts`：最前面加一筆、`CONTENT_VERSION` +1（單元測試守著）。
- `src/i18n/zh-TW.ts` 加 `changelog.vNN`：系統口氣、不劇透、台灣用語、≤ 36 字。
- 改了數字 → `docs/02-balance.md` 變更紀錄加一列（用 balance-tuning skill）。
- 使用者拍板的事 → `docs/14-open-questions.md` 把 Q 改成已回答、寫下原話。
- 新規則或新工具 → `CLAUDE.md` 索引表加一行。**新增「要記得做」的規則時，同時做一個會自動擋下來的檢查**（使用者 2026-11-14 的要求）。

## 3. 提交與推送

直接推 main（不開 PR）。提交訊息用中文寫做了什麼，結尾照當次 session 的附註加 `Co-Authored-By` 與 `Claude-Session` 兩行（看系統提醒裡的最新版本）。

```bash
git add -A && git commit -q -F - <<'MSG'
<一句話：做了什麼（D/Q 編號）>

Co-Authored-By: ...
Claude-Session: ...
MSG
git push -q origin main
```

## 4. 更新測試頁

用 publish-test-page skill（打包、打包檔檢查、發佈）。**主網址只有使用者說「發佈」才動。**

## 5. 回報（使用者規定的格式）

1. **先做合理性自我審查**：把要送的截圖逐張讀過、逐字讀畫面上的字，問「玩家看到會不會覺得怪」；新內容碰到的共用畫面（選卡、暫停、HUD、神社、結算）都要看。
2. **截圖**：用 `SendUserFile` 送 2～4 張（手機直式優先），caption 寫每張是什麼。沒有畫面變動的改動（純數字、純文件）不用。
3. **文字**：
   - 先講結論和連結（測試頁、版本號）。
   - 做了什麼（玩家看得懂的話；表格比條列好讀）。
   - **驗證了什麼**：哪些測試、哪些截圖、哪些模擬數字。
   - **沒覆蓋的類別**：不要寫「其他應該沒問題」。要真人判斷的（手感、好不好玩）明講。
   - 過程中發現並修好的問題也要說（使用者重視誠實）。
   - 有要使用者決定的事，最多 3 件、每件附預設。
   - **最後一定要列「接下來三項」**（使用者 2026-11-17：「以後做好一個項目都要提示接下來的三個進度」）：照 `docs/05-schedule.md` 第 1.0 節「接下來三項」（先把剛做完的移掉、補上下一項，再回報），每項一句話＋工作量。單元測試 `nextUp.test.ts` 守著那一節。
