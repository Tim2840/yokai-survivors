# 改平衡數字

數字全部在 `src/data/`（程式碼裡不准有平衡用的魔術數字）。使用者不是專業設計師，他說的是感覺（「後期沒挑戰性」）；我要把感覺翻成量得到的指標，用模擬證明改動有效，再交給他試玩。

## 1. 先量現況，再動手

```bash
npm run sim -- --runs 20                     # 約 3 分鐘；桌機上限、召喚頭目在 50%
npm run sim -- --runs 20 --mobile            # 手機的同畫面上限（200 隻）
npm run sim -- --runs 20 --summonAt 0.9      # 機器人打到倒數後段才召喚頭目（看「後期」一定要加）
npm run sim -- --only dps,survive --elements on   # 只跑部分組合（快）
```

每一行是「選卡策略／用不用地圖要素」：random（亂選）、dps（偏輸出）、survive（偏防禦）。看這幾個數字：

- **過關率**、存活時間 P10/P50/P90、等級、擊殺。
- **四個時段的場上敵人**與**每分鐘被打掉的生命**（括號裡）——判斷「前期／後期難不難」用這個，不要只看平均。
- 技法數、技法等級合計、進化率——判斷養成速度。
- 20 局的雜訊約 ±10 個百分點；差距小於這個不要下結論。

**坑**：預設機器人在 50% 召喚頭目、打完就離開，關卡後段幾乎沒被模擬到。問「後期」一定要 `--summonAt 0.9`。

## 2. 用 --tune 做對照（不用改檔）

```bash
npm run sim -- --runs 20 --tune "techChance=0.5,rarity.unlock=4,late.mult=1"
```

可調的前綴（`scripts/sim/sim.ts` 的 `applyTune` 有完整清單，新旋鈕要加進去）：`xp.`（PROGRESSION）、`w.`（WAVES）、`tech.`（TECH_OFFER）、`shards.`、`chapter.`、`summon.`、`drops.`、`late.`、`recycle.`、`rarity.<階>.<欄位>`、`rarity.unlock=4`、`rings=off`、`recipes.<敵人>=0`，其他名字直接改 `tuning`（例：`techChance`、`countScale`、`hpScale`）。

做法：**新值寫進 src/data，舊值用 --tune 還原**，兩組一起跑，結果並排比較。改動前後都要跑。

## 3. 想清楚因果，別只加數字

這個專案已經學到的：
- **只加敵人數量不會變難**：玩家殺得夠快，多生的敵人變成多的經驗、等級更高。要一起動血量、經驗（Q60：速率 ×2、血量 ×4、經驗 ÷ 速率倍率）。
- 手機有同畫面上限 200，數量多到上限就看不出來。
- 解鎖、上限這類開關會讓別的設計「突然生效」（Q60 開放珍、極後，里程碑保證的極卡被技法卡蓋掉才浮出來）——開關改了要掃一遍依賴它的地方。
- 新角色或新招要對照同類的數字（sim 基準）：差太多先調再報。

## 4. 記錄（規則：數字改動要有依據）

- `docs/02-balance.md` 最後的變更紀錄表加一列：`| 日期 | 改了什麼（舊 → 新） | 理由（使用者原話） | 驗證（sim 指令與並排數字） |`。
- 公式或表格在 docs/02 正文也有的，同步改。
- 守數字的單元測試（例：`tests/unit/balanceData.test.ts` 的稀有度機率）要一起更新，**更新前先確認失敗的原因真的是你改的那個數字**。
- 新加的機制要有「舊版會紅」的單元測試。
- 使用者還沒拍板的大改動（會改到別的已決定設計），先交設計審查卡（design-review-card skill），不要直接改。

## 5. 回報

用表格並排「改前 → 改後」，標明是哪種模擬（手機／桌機、召喚時間點）、雜訊範圍，並明講「機器人不是真人，手感要試玩」。數字放在哪個檔、哪個欄位也要講，方便使用者說「再難一點」時直接調。
