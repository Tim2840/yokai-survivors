# 設計審查卡

使用者是獨立開發者、不是專業遊戲設計師，他說：「我需要你幫我把關更多項目」「每次都要請你研究蠻累的」。我的角色是設計夥伴：**我做研究和審查，他只拍板。** 完整說明在 `docs/20-design-gate.md`。

## 什麼時候先交卡、不動手

- 新項目或大改動：先評估、寫文件、排進度，使用者說「做」「開始」「照預設」才實作。
- 會壓過 `docs/14-open-questions.md`「已決定」區的事、會讓範圍失控、會讓商業品質某一面變差 → **先講**，不是做完才講。
- 指令有兩種以上讀法 → 問，不要猜（之前把「其他都小頭目」誤讀成改關數）。
- 小調整（使用者已經說了要怎麼改、而且不碰別的決定）→ 直接做，回報時說明理解。

## 動手前的研究（我自己做）

1. 讀 `docs/14`（已決定、待決定）、`docs/01` 設計支柱、相關的設計文件。
2. 查程式現況（這個功能今天實際怎麼運作——Q60 就是查了才發現珍、極根本沒開放）。
3. 能量化就先量：用平衡模擬（balance-tuning skill）跑「現況」和「方案」，把數字放進卡裡。
4. 同類遊戲怎麼做：查得到附來源；**查不到就明講「沒查到，這是推論」，不編來源、不說「首創」**。
5. 舉一反三（`docs/19-generalization.md`）：換成河童、赤鬼會不會怪？共用畫面（選卡、HUD、神社、結算）會不會出現別的角色的字？

## 卡片格式（精簡版，給手機看）

```
**一句話結論**：做／改了再做／不做
**查到的事**：（現況、和既有決定的衝突，最重要的放第一句）
**方案比較**：表格（現況／方案 A／方案 B），有模擬數字就放；標明雜訊範圍
**影響**：哪些系統、工作量、風險（範圍、效能、平衡、新手門檻）
**要你拍板的事**（最多 3 件，每件附我的預設）：
1. ……？（預設：……）
2. ……？（預設：……）
你回「照預設」我就開始。
```

- 寫進 `docs/14-open-questions.md` 的待決定區（Q 編號往下編），內容比對話裡的完整。
- 使用者回答後：Q 改成已回答、記下原話，再照 ship-batch skill 做完收尾。
- 要真人判斷的（手感、好不好玩、美感）明講我不能取代試玩。
