# 05 開發進度計畫（業界標準階段版）

> 版本 v0.2（2026-11-03）：加入 M2b 風格基準與美術音樂精緻化排程（第 2.2 節），M3 起日期順延 2 週、M7 延長為 4 週（M8、M9 因此再順延 2 週，合計上線目標 5/16 → 6/13）。依遊戲業界常見的階段與「關卡門檻（Gate）」制度編排：**概念 → 前期製作（原型、垂直切片）→ 製作（Alpha、Beta）→ 發行前（候選版）→ 上線 → 營運**。每個門檻都有「進入條件」與「驗收標準」，沒過就不進下一階段。

## 0. 前提與估算方式（請先看）

- **團隊**：1 位產品負責人（使用者，決定方向、試玩、點頭）＋ AI 協作者（程式、測試、文件、美術程式化、平衡模擬）。沒有外部美術與音效人員。
- **時間單位**：「週」= 使用者每週大約進行數次 session 的工作量。**日曆日期是以 2026-11-09 開始、每週穩定進度推算的目標日期，不是承諾**；實際取決於使用者的可用時間與試玩回饋次數。估計誤差約 ±30%，第 8 節列出了最容易延誤的項目。
- 規模控制：首發 = 3 隻妖怪 × 5 張地圖 × 6 種人類＋精英＋5 頭目 × 9 種要素 × 約 40 張卡片。其餘（新妖怪、新地圖、語言）都排在上線後。

## 2. 里程碑明細

每個里程碑有：**目標、交付物、驗收標準（Exit）、測試重點、主要風險**。

### M0 專案骨架（W1，11/09–11/15）

- 目標：能開發、能測、能打包、規矩就位。
- 交付物：Vite+TS+Three 專案、狀態機骨架、事件匯流排、資料目錄、`i18n` 骨架、存檔骨架、Vitest（假 localStorage）、Playwright 回歸腳本骨架（`regress.mjs`、`lib.mjs`）、單檔打包（`build:single`／`build:single:main`）、`__game` 開發介面、CI（GitHub Actions：typecheck＋test＋build）。
- Exit：`npm run typecheck && npm test && npm run build` 全綠；一張空場景能載入並在手機與桌面各截一張圖。
- 風險：低。

### M1 原型（W2–W3，11/16–11/29）→ 門檻 **G1「好玩嗎」**

- 目標：驗證**核心手感**，這是整個專案最重要的一個驗證。
- 交付物：固定俯角鏡頭（先 50°，調參數檔）；一隻領頭妖怪（提燈小僧）在一塊有高度差的平地上 WASD／搖桿移動；自動鬼火攻擊；`InstancedMesh` 的村人 200～400 隻；擊退、命中閃白、傷害數字（物件池）；20 秒波次計時；升級→暫停三選一卡片（D15，4 張屬性卡就好）→波次結束進整備；Bloom；死亡與重來。
- Exit（G1）：使用者實際玩 3 局，回答「想再玩一局嗎？」；手機 30 FPS 以上（400 敵人）、桌機 60 FPS。**不是 G1 通過就不往下**：若手感不對，調整核心再重做 M1（這是最便宜的時間點）。
- 測試重點：效能預算（docs/06 第 6 節）、碰撞正確性單元測試、固定時間步長。
- 風險：中——固定俯角鏡頭在有高低差時是否看得清；手機效能。

### M2 垂直切片（W4–W7，11/30–12/27）→ 門檻 **G2「垂直切片」**

- 目標：一局**完整**（選妖怪→20 波→頭目→結算），品質接近成品，用來決定視覺風格與驗證所有系統能合在一起。
- 交付物：資料驅動的屬性／稀有度／卡片系統（docs/02 第 4、5 節）；3 隻初始妖怪（含號令與小妖）；5 種基礎人類＋1 個頭目；地圖 1（夜之村田野）含 3 種地形與高低差；地圖要素 **3 種**先做（詛咒祭壇、石地藏、賽錢箱）驗證要素框架；`npm run sim` 平衡模擬 v1；基本 HUD（血條、波數、屬性面板）；基本音效與一首音樂；功德結算畫面。
- Exit（G2）：使用者通關（或接近）一局；30 張以上的卡片可抽；模擬與真人試玩的「可撐波數」落差在 ±3 波以內；無 pageerror；手機直式／橫式／桌面三種版面通過 `layoutcheck`。
- 風險：高——這是範圍最大的里程碑；若超時，拿掉「3 種要素」改成 1 種。

### M2b 風格基準（W8–W9，12/28–1/10，新增）→ 門檻 **G2b 風格定案**

見第 2.2 節。目標：用「一隻妖怪＋一個主畫面＋兩首曲子」把視覺與音樂的精緻度**定在一個使用者點頭的水準**，之後所有內容照這個水準複製。

### M3 局外成長與要素（W10–W13，1/11–2/7）

- 目標：重玩循環完整：死了→結算→商店→再玩。
- 交付物：存檔系統（含「重載後還在」測試）；局外商店四個分頁（修行、卡池、秘術、圖鑑簡版）；功德結算；要素補到 9 種；神籤、狐面商等狀態效果系統（限時 buff／debuff 系統）；夜深度 0～2；更新紀錄機制（`changelog.ts`）；首次遊玩教學（用做中學，**高亮要素且測試走完**）。
- Exit：新玩家（使用者找的 1～2 位朋友）不看說明能完成第一局與第一次購買；存檔相容性測試；經濟模型 v1 校準（docs/02 第 7.4 節的總局數是否合理）。
- 風險：中——教學和 UI 的錯誤率（從燈落之境學到的：必須用真實點擊走流程）。

### M4 內容一（W14–W17，2/8–3/7）

- 交付物：地圖 2（河童之淵，含漲潮）、地圖 3（竹林迷徑，含濃霧）；全部 6 種人類＋精英；頭目 2 隻；遺物系統與 12 件遺物；人類圖鑑（民俗小故事 草稿要先給使用者點頭）；小妖補到 5 種；卡池達約 40 張。
- Exit：每張圖都能從頭玩到尾；`sceneaudit`（物件／碰撞）與 `perfcheck`（著色器編譯 0）過關。

### M5 Alpha（W18，3/8–3/14）→ 門檻 **G3 Alpha**

- 定義：**功能完整（Feature Complete）**——所有系統都存在、可玩，內容可以是暫時的。
- Exit：本文件第 1 節首發範圍內的所有「系統」都實作過；已知的當機型錯誤為 0；全套回歸跑一次（記錄時間）。

### M6 內容二（W19–W22，3/15–4/11）

- 交付物：地圖 4（山寺石階）、地圖 5（荒城）；全部 5 位頭目；夜深度 3～5；妖怪收集（方案 A，docs/04 第 5 節）；天狗與雪女之一先做（若 Q5 決定首發含收集妖怪）。
- Exit：所有內容都放進遊戲（Content Complete 的前一步）。

### M7 Beta（W23–W26，4/12–5/9，由 2 週延長為 4 週）→ 門檻 **G4 Beta**

- 定義：**內容完整（Content Complete）**——只剩修錯與打磨，不再加新內容。
- 工作：完整平衡校準（模擬＋真人）、音效音樂補齊、介面全面打磨、無障礙（色盲標示、字級）、手機操作優化。
- Exit：封閉測試 5～10 人，回收問卷；致命錯誤為 0；平均一局時間、第一次通關率、留存（第二局開始率）有數據。

### M8 候選版（W27–W29，5/10–5/30）→ 門檻 **G5 RC**

- 工作：效能最佳化（低階手機）、載入時間（首次 ≤ 30 MB）、PWA／離線、錯誤回報機制、商店頁素材（截圖、短影片、說明文字）。
- Exit：連續一週沒有新的致命錯誤；三種版面 × 全部地圖 × 三隻妖怪的冒煙測試全過。

### M9 上線（W30–W31，5/31–6/13）→ 門檻 **G6 Go**

- 工作：發佈到 docs/14 Q6 決定的平台（先是網頁平台），上線檢查表（docs/07 第 9 節），上線後 72 小時緊急修補值班。
- Exit：上線；沒有 blocker 回報。

### 營運（W32 起）

- 內容更新週期暫定每 6～8 週一次：新妖怪、新地圖、新要素、新語言（日文、英文）、排行榜。
- 以第一個月數據決定投資方向（見 docs/13 的指標表）。

### 2.2 美術與音樂精緻化排程（2026-11-03，使用者要求：主畫面、妖怪模型、音樂要做得更精緻，不要只是幾個旋律拼接）

評估與天花板在 docs/08 第 7 節。排程原則：**先定水準、再複製**；每一階段使用者親自看與聽、點頭才往下。

| 階段 | 時間 | 美術（主畫面、妖怪、人類） | 音樂 | 使用者審查 |
|---|---|---|---|---|
| M1（原型） | W2–W3 | 提燈小僧**簡易版**（先求剪影與動作可讀）；搬角色展示間 | 不動（現有 3 首當佔位） | 無 |
| M2（切片） | W4–W7 | 簡易版延用；村人 3 種簡易版 | 音樂引擎 v2 的**設計文件與測試工具**（離線渲染、頻譜、迴圈接縫檢查）；不做曲子 | 無 |
| **M2b 風格基準** | **W8–W9** | ①提燈小僧**精緻版**（展示用高細節＋戰鬥用低細節兩套，含描邊、表情、次級動作）②**主畫面 v1**（3D 舞台、鳥居、燈籠、月、螢火、標題字）③從展示間／選角／主畫面三個角度驗收 | ①引擎 v2：三味線、尺八、太鼓、琴音色；曲式 A–B–A′–C（約 64 小節）；變奏產生器（同動機的移調、反行、節奏變化，固定種子）②**標題曲與村田野戰鬥曲各一首完整版**（每首 ≥ 2 分鐘不重複感）③戰鬥曲分 3 層強度（跟波次與頭目連動） | **G2b**：使用者看圖、聽曲，回答「這個水準可以當全遊戲基準嗎」；不行就在這個點調整 |
| M4 內容一 | W14–W17 | 河童、赤鬼精緻版；人類 6 種（普通版）；地圖 2、3 的場景氛圍 | 地圖 2、3 戰鬥曲各一首；整備曲 | 每首曲子完成後使用者聽 |
| M6 內容二 | W19–W22 | 頭目 5 隻（精緻版，展示＋戰鬥）；地圖 4、5 氛圍；新妖怪 1 隻 | 地圖 4、5 戰鬥曲、頭目曲 2 首、結算曲、商店曲 | 同上 |
| M7 Beta | W23–W26（延長 2 週的主因） | 主畫面**最終版**；全部圖鑑展示與選角畫面打磨；特效（命中、鬼火、水浪）統一調 | 全部曲子**混音與響度統一**、迴圈接縫、過場短句（stinger）、音效與音樂配比 | **G4** 前使用者整體審一次 |

**驗收方式（我能量、使用者才能判斷的分開）**
- 我能驗證：音樂離線渲染後的峰值、響度、頻譜、迴圈接縫、音階內的音、曲長（無重複的秒數）；模型在戰鬥比例下的剪影（桌面 74 px、手機約 40 px）、各角度截圖、`scaleaudit`；主畫面三種畫面不破版、載入時間。
- **只有使用者能判斷**：旋律好不好聽、音色像不像三味線、角色可不可愛、主畫面有沒有氣氛。**我沒有耳朵，這部分沒有使用者點頭就不算完成。**

**風險與可砍清單（砍的順序）**：①M7 的特效統一調 ②地圖 4、5 的專屬曲改為共用曲＋變奏 ③精緻版只做提燈小僧與河童，赤鬼用簡化版 ④主畫面最終版沿用 v1。

## 3. 關鍵路徑

```
M0 骨架 → M1 原型(G1) → M2 資料驅動系統 → M3 存檔＋商店 → M5 Alpha → M7 Beta → M8 RC → 上線
```

任何一步晚了，後面全部順延。**可以平行做、不在關鍵路徑上的**：美術風格與色票、音樂、民俗小故事草稿、i18n 字串、商店頁素材。

## 4. 每個里程碑的固定動作

1. 開工前：讀 `docs/09-handoff.md`、列出本里程碑的待辦到任務板（`docs/11-risks-backlog.md`）。
2. 做的過程：每個系統「先寫資料與測試、再寫程式」；改數字就寫變更紀錄。
3. 收尾：跑相關回歸（`--only`）＋ `npm test` ＋ `typecheck`；更新 `docs/09-handoff.md`；更新測試頁；報告「驗證了什麼／沒覆蓋的類別」。
4. 門檻審查：用該門檻的清單逐條對，回報給使用者決定要不要進入下一階段。

## 8. 最容易延誤的事（Top 5）

1. **M1 手感不對**要重做：越早發現越便宜，所以 G1 一定要真人玩。
2. **高低差＋固定鏡頭的可讀性**（高物件遮住玩家）：M1 就要驗證，不要等到做地圖才發現。
3. **手機效能**（400 隻敵人＋Bloom＋水面著色器）：M1 就開始量，M8 才調會來不及。
4. **平衡反覆**：M2 的模擬工具如果延遲，後面所有數字都靠猜。
5. **教學與 UI 的錯誤**（燈落之境的重傷區）：每個教學都要有「照著高亮走完」的回歸。
