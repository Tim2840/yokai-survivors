# 07 測試與品質保證（QA）計畫

> 版本 v0.1（2026-11-03）。從燈落之境的慘痛經驗來：**舊測試呼叫內部函式、只測桌面，玩家卡住也全綠。**所以本專案的測試金字塔把「真實玩家路徑」放在最重的位置。

## 1. 測試層級

| 層 | 工具 | 測什麼 | 何時跑 |
|---|---|---|---|
| 1 單元 | Vitest（node，假 `localStorage`） | 公式（護甲、傷害）、稀有度抽選、資料結構檢查、狀態機轉換、存檔合併與遷移、i18n 掃描、`Rng` 可重現、空間雜湊、地形查詢 | 每次提交（約 1 秒） |
| 2 模擬 | `npm run sim`（無頭，Node） | 平衡：可撐波數、DPS 曲線、各妖怪勝率、要素對勝率的影響、經濟（功德→購買進度） | 改任何 `src/data` 前後 |
| 3 回歸 | Playwright（真瀏覽器） | 真實玩家路徑：點擊選妖怪→打→選卡→死亡→結算→購買→重載後還在；3 種畫面尺寸 | 相關改動；Alpha 起每週全套 |
| 4 稽核 | 專用腳本 | `layoutcheck`（介面不重疊、不超出）、`perfcheck`（著色器編譯 0、FPS、draw call）、`glowaudit`（光暈大小）、`scaleaudit`（模型比例）、`musiccheck`、`sceneaudit`（物件、碰撞） | 相關改動；RC 前全跑 |
| 5 人工試玩 | 使用者與測試者 | 手感、好不好玩、難度、平衡、可讀性 | 每個 Gate |

## 2. 回歸測試的必守規則（照搬燈落之境的教訓）

1. **只用真實點擊／觸控走流程**（`page.mouse.click`、`touchscreen.tap`），不呼叫內部函式；起點放在合理位置，不用 teleport 走捷徑（除非測的是別的東西）。
2. **三種畫面各跑一次**：手機直式（390×780）、手機橫式（800×390）、桌面（900×600 與 1280×720）。
3. **卡住偵測**：畫面狀態（目前狀態、卡片、按鈕位置、彈窗）連續 12 輪沒變且流程未完成 → 失敗並印出最後狀態。
4. **對照組要在同一刻同一狀態量**；結果看起來隨機時，先找哪個狀態留到下一個案例。
5. **「舊版會紅」**：修正錯誤時一定要附一個在舊程式碼上會失敗的測試。
6. **無頭瀏覽器 1～2 FPS**：用 `waitForFunction` 或 `__game.advance` 快進；截圖前 `__game.render()`；測「重載後還在」用 `page.reload()`。
7. 每支回歸登記 id（唯一）、`stall`（步驟接近 45 秒）、`max`（該支允許的總時間）。
8. 量「被打扣血」要關掉 `god`。
9. 教學／提示／高亮只要改動，必跑 `regress --only u6`（教學走完：只點高亮處、三種尺寸、卡住偵測）。新教學先加進 u6 的 `SCENES` 再寫。

## 4. 平衡模擬（`npm run sim`）

- 一個無頭的模擬器，直接匯入 `src/data` 與 `src/systems` 的**純邏輯部分**（不碰 Three.js），跑成千上萬局。
- **模擬玩家策略**：貪心選卡（依「對 DPS 提升」打分數）；移動策略簡化為「固定風箏圈」；提供 3 種策略（亂選、貪 DPS、貪生存）。
- 輸出：每波的敵人總 HP vs 玩家 DPS、可撐波數分佈（P10/P50/P90）、各妖怪勝率、各要素的淨影響（接受 vs 不接受的勝率差）、功德收入與商店購買進度。
- **使用規則**：任何 `src/data` 變更，PR 要附 sim 前後對照；若某妖怪勝率偏離平均 ±15 個百分點，就要調。
- 模擬器**不能取代真人試玩**；兩者落差要在 G2 前收斂到 ±3 波。

## 5. 卡片與要素的資料檢查（全掃）

- 每張卡、每種要素、每個地形×妖怪組合：單元測試用資料表「全掃」，確認有 i18n、有圖示、有四階數值、數值單調遞增（稀有度越高越強）、不低於地板／不超過天花板。
- 要素組合測試：把所有「詛咒祭壇」的合法升降配對全部套用到最差狀態，驗證屬性不跌破地板（見 docs/02 第 2 節）。

## 6. 錯誤分級

| 級別 | 定義 | 處理 |
|---|---|---|
| S0 致命 | 當機、存檔損毀、無法進行／無法離開的卡住 | 立刻修，修完加回歸 |
| S1 嚴重 | 錯誤的數值（難度失控）、進度遺失、版面破壞 | 本里程碑內修 |
| S2 一般 | 外觀瑕疵、輕微不順 | 排入待辦 |
| S3 建議 | 想法與優化 | 待辦清單 |

Alpha 之後：S0 為 0 才能過門檻；Beta 之後 S1 為 0；RC 之後 S2 ≤ 10 個且都已知。

## 7. 回報格式（每次完成一批工作時）

```
驗證了什麼：（列出具體測試與結果，附數字）
沒覆蓋的類別：（明確列出，不寫「其他應該沒問題」）
已知問題：（編號、分級）
```
