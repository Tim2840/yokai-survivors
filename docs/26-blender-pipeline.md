# 26 引入 Blender（設計審查卡；**試作已完成 D87，等使用者看過決定 Q54**）

> 使用者 2026-11-12：「blender 的引入也要提上日程」。延續 Q47（「不要只用我們目前有的資源，請想別的辦法大大提昇精緻度」）。

## ① 一句話結論
可以做，而且是提升角色與場景精緻度最直接的路；但它會**推翻一條鐵則（CLAUDE.md：「不使用外部模型檔，所有模型用程式碼建出來」）**，並且要先解決「模型誰做」。建議排在這一批（河童新機制、平衡）之後，先做一個**小型試作（1 個角色＋1 個場景物件，約 2～3 天）**確認整條流程走得通，再決定要不要全面換。

## ② 現況
- 所有模型都是 TypeScript 用基本形狀拼出來的（`src/units`、`src/art/shapes.ts`），每隻約 700 個三角形以內；優點是檔案小（整個遊戲單一 HTML 約 0.9 MB）、風格統一；缺點是造型的精緻度有上限（你已經說過不滿意）。
- 測試頁與主網址是**單一 HTML 檔**（Artifact），外部檔案載不進來，模型必須**內嵌**在檔案裡。

## ③ 做法（三條路）
| | A 我用 Blender 的 Python（bpy）寫腳本建模 | B 你（或外包）在 Blender 手動建模 | C 用現成的免費素材（CC0） |
|---|---|---|---|
| 精緻度 | 中上：修改器（倒角、細分、布林）、骨架、頂點色，比現在好一截；但我看不到畫面只能靠算圖檢查 | 最高 | 看素材 |
| 風格一致 | 高（同一套腳本） | 看人 | 低（要挑、要改色） |
| 誰出力 | 我 | 你／美術 | 我挑、你同意 |
| 風險 | 腳本建模的上限仍低於手工 | 你說過你不是美術；外包要錢 | 之前查過：這個環境連不到幾個素材站（kenney、quaternius、itch、opengameart 被擋）；授權要逐一確認 |
- 三條路的下游都一樣：**Blender → 匯出 glTF（.glb）→ 壓縮 → 內嵌進單一 HTML → 遊戲用 GLTFLoader 載入**。
- **我查到的事實**：這個環境裡沒有安裝 Blender；套件庫上有 `bpy`（Blender 的 Python 模組，5.3.0），**還沒有實際安裝、跑過**——能不能在這個環境無頭執行、匯出 glTF，是試作第一步要驗證的事，現在不能保證。

## ④ 要先講的代價
- **檔案大小**：一個帶骨架動畫的 Q 版角色約 100～300 KB（壓縮後）；10 個角色＋場景物件會讓單一 HTML 從 0.9 MB 變成 3～5 MB（Artifact 上限 16 MB，夠用，但載入變慢）。
- **效能**：手機的繪製次數已經 77／80。敵人是 `InstancedMesh`（一種敵人一次繪製）——**帶骨架的模型不能直接這樣畫**，200 隻敵人要改用「頂點動畫貼圖」或維持現在的程式動畫（只換網格）。玩家與頭目（各 1 隻）可以直接用骨架。
- **像素風**：畫面會像素化＋卡通著色，模型太細的細節會被吃掉；重點是**輪廓與比例**，不是面數。
- **鐵則要改**：CLAUDE.md、docs/06（架構）、docs/08（美術）要改成「模型可以用 Blender 做，來源檔（.blend 或建模腳本）放進版本庫」。
- **流程變重**：改一個模型要重跑匯出；測試（三角形數、動畫名稱、大小預算）要新做。

## ⑦ 試作結果（D87，2026-11-12；Q53 三件都照預設）

**做了什麼**：用 Blender 的 Python（`bpy` 5.3，無頭執行，不進版本庫）寫腳本建了兩個模型，匯出 `.glb` 內嵌進測試頁。
- `tools/blender/lib.py`（建模小工具：球、錐、盒、環、車削、頂點色、骨架、動作、匯出）、`tools/blender/build.py`（提燈小僧、鳥居）。
- 重建指令：`python3 tools/blender/build.py <bpy 安裝目錄> src/assets/models`（`pip install --target <目錄> bpy`，約 1.1 GB）。
- 遊戲端：`src/units/blenderModels.ts`（GLTFLoader 解析、材質換成遊戲自己的卡通材質、骨架動畫 walk／idle 混合）。
- **只有網址帶 `?model=blender` 才載入**（開發版與測試頁）；主網址的打包不含（`check:main` 通過、打包檔裡 0 筆 glb）。現有模型完全沒動。

| 項目 | 現有（程式建模） | Blender 試作 |
|---|---|---|
| 提燈小僧的細節 | 斗笠、僧衣、燈籠（幾何體拼接） | 多了交領、腰帶結、斗笠編線與下巴繩、白襪木屐、竹節、燈籠骨架條紋、眉毛腮紅 |
| 動作 | 程式擺動（上下彈、腳前後） | 骨架動畫：走路 16 格、待機 48 格（手、腳、頭、燈籠各自動） |
| 繪製次數（手機直式，同一鏡頭） | 95 | 69（角色從多個零件變成 2 個網格；另含一座鳥居） |
| 著色器程式 | 48 | 52（多了骨架版本；p1 的上限要跟著調） |
| 面數 | — | 提燈小僧 4505、鳥居 1176 |
| 檔案 | 0 | 319 KB＋88 KB；測試頁 904 KB → 1548 KB（含 GLTFLoader；base64 內嵌會膨脹 1.33 倍） |

**驗證了什麼**：兩個模型在遊戲裡載得進來、吃同一套光影／邊緣光／像素化；手機直式與桌面各 3 個鏡頭的並排截圖（`scripts/shots/blender.mjs`，`screenshots/blender-t2-*`）；typecheck、單元測試、`check:main`。
**沒覆蓋的**：①只做了提燈小僧，河童沒做；②化身（變大）、受傷閃白、大招時的模型效果沒接到 Blender 版；③沒量真機幀率（只看繪製次數）；④回歸測試沒有帶 `?model=blender` 跑過；⑤手機上像素化之後，新增的細節（竹節、編線）有一部分看不出來，最有感的是輪廓、臉與鳥居；⑥腳本建模的上限仍是「幾何體組合」，做不出手雕的有機造型——那要真人美術（路線 B／C）。
**我的看法**：場景物件（鳥居這類）進步最明顯、成本最低；角色的進步主要在動作與輪廓。檔案變大是主要代價（每個角色約 +0.4 MB）。


## ⑧ 使用者不滿意，給參考圖（2026-11-12，Q57）

參考圖：《妖怪手錶 World》宣傳圖。**只學風格，不使用任何角色**（那是 Level-5 的作品）。我從圖上看到的特徵（我的觀察，不是官方設定）：
1. **畫面不像素化**，邊緣乾淨；描線細、偏暗色不是純黑。
2. **高飽和的色塊**：紅、藍、白為主，每個角色一個主色，暗部是同色系偏暖偏深，不是灰黑。
3. **對比**：角色顏色比背景鮮豔得多（背景偏寫實、偏灰綠），角色一眼跳出來。
4. **造型**：頭大、身體短胖、四肢短；**眼睛大、有明顯高光**，臉是整個角色的重點；常有一個「記號」（貓尾、風呂敷、漩渦紋）。
5. 有光澤感（高光點）、半透明發光（幽靈）。

**為什麼 Blender 第一版不像**（我的判斷）：①建模方向本來就跟「像素風＋Q 版」配；顏色取自現有的柔和色票（米白＋淺橘），**對比弱**；②畫面還是像素化＋偏黃的白天光；③身上的玩家光讓角色曬到發白；④Blender 只提升細節（交領、編線），**不是這種風格要的東西**（要的是色塊、對比、臉）。

**樣張（`?look=cel`，只有開發版與測試頁能看）**：新增 `cel` 畫面風格——不像素化（短邊 1100）、飽和度 1.45、暗部亮度 0.62、描線偏暖；Blender 版提燈小僧調高飽和色票、眼睛加大並加藍色虹彩。**結果：比原本鮮豔，但離參考圖還很遠**——角色仍是米白＋橘、臉在多數鏡頭看不到、玩家光過曝、地面仍有方塊紋。要真的做到，需要：①角色重新配色（主色＋強對比輔色）②臉朝向鏡頭的相機／出場姿勢③降低玩家身上那盞光的過曝④描線與抗鋸齒（目前的後製是最近鄰取樣、沒有抗鋸齒，高解析度下邊緣會閃）⑤地面與背景降飽和，讓角色跳出來。**這是一個里程碑等級的工作（約 4～6 天），而且推翻 D72，所以先不做，等你回答 Q57。**
**沒驗證的**：沒在真機看、沒跑回歸、沒量幀率；「正面」截圖其實拍到背面（相機角度弄錯），所以臉的樣子還沒有看到。
