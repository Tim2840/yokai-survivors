> 這份是**給每次新增內容前先讀的檢查表**。已發生的錯、可預見的場景、各自的防線都列在第 3 節，狀態會更新。

## 1. 研究摘要（來源與限制）

- **道具正交（item orthogonality）**：一個小的道具池，和遊戲裡的許多對象各有互動，而不是一個道具只做一件事。→ 本專案的通用法具（多重、碎裂、穿透、廣域…）要和每隻妖怪的武器都「有互動」，沒互動的不該出現。來源：[Roguelike Item Orthogonality](https://www.gamedeveloper.com/design/roguelike-item-orthogonality)、[roguelike item and monster design revisited](https://www.gamedeveloper.com/design/roguelike-item-and-monster-design-revisited)（Game Developer 部落格；取自《風來的西蓮》的原則：道具對玩家、怪物、NPC 盡量用同一套規則）。
- **系統性設計（systemic design）**：道具、敵人、地形、狀態、資源用可重複使用的方式組合，而不是各自孤立的內容。→ 分類、狀態、地形效果要寫成通用規則，角色只提供資料。（來源：同上搜尋結果中的 game-designer skill 描述，是二手摘要。）
- **功能資料與風味資料分開**：機制識別碼放底層，名稱／風味放上層，改名不改行為。來源：[Data-driven Design: A Case for Maximalist Game Design](https://arxiv.org/pdf/1805.12475)（《A Rogue Dream》的能力名稱來自開放資料，名稱不影響效果）。
- **吸血鬼倖存者的做法**：被動道具大多只為了讓某把武器進化而存在，也就是「道具的意義是相對於武器」。來源：搜尋結果的玩家攻略（二手，僅供參考）。
- **限制**：我**沒有找到**直接討論「通用道具放到近戰／遠程不同角色上沒效果怎麼辦」或「命名要依功能不依屬性」的權威資料。下面第 2 節的原則是我從上面幾條**推論**出來的，不是業界公認的規範。

## 2. 本專案的原則

1. **機制名、分類名依「怎麼運作」命名，風味名只放在角色專屬的層**（主武器、技法、進化、大招、模型）。燃燒、火焰、水、金屬都不能出現在通用名稱裡。
2. **每個通用的東西，新增或接到新角色時都要回答三個問題**：①放到這隻妖怪的武器上**有沒有效果**？②名字和說明**換成河童、赤鬼還說得通**嗎？③它的**顏色、圖示、音效**是寫死某隻妖怪的嗎？
3. **角色專屬一律是資料**（`YOKAI`、`WEAPON_LEVELS`、`TECHS`、`EVOS`、`ULTS`、`palette.fx`、`units/*`），共用的系統只讀資料，不寫 `if (yokai === 'kappa')`。
4. **同一份資料餵畫面、測試與 sim**（單一來源），新增角色時由測試列出漏的項目，而不是靠我記得。
5. **全掃，不用清單**（沿用既有規則）：新角色進 `PLAYABLE_YOKAI` 的那一刻，`yokaiCompleteness.test.ts` 會一次列出缺什麼。
6. **敵我對稱**：玩家方與人類方盡量共用同一套狀態與傷害規則（取自上面的原則）；新增狀態先想敵方會不會也要用。

## 4. 每次新增內容前的 5 個問題（也寫進 CLAUDE.md）

1. 這個東西**每隻妖怪都會看到**嗎？是 → 通用名詞、通用規則。
2. 放到**揮擊、回力、投射物**三種武器上各有沒有效果？
3. **換成河童、赤鬼**名字和說明還說得通嗎？
4. **顏色、圖示、音效**是寫死某隻的嗎？
5. 我只檢查了新東西，還是也掃了**它碰到的每個共用畫面**？
